# 🏗️ 技術選定理由 (Architecture)

本システムで採用した技術スタックと、選定した理由について記述します。

---

## 1. フロントエンド / ホスティング
* **Next.js (App Router)**
  * **選定理由:** 以前Laravelを触った際の体験と比べて、Next.jsのApp Routerはフォルダ構造がそのままURLになるため直感的で扱いやすいと感じたことと、Webアプリ開発で最近特によく使われているフレームワークだと聞いたため採用しました。
* **Vercel**
  * **選定理由:** Next.jsの開発元であるため、同じサービスで揃えることで設定の手間や予期せぬトラブルを減らせると考えたためです。実際にCloudflare Pagesにリポジトリをデプロイしたこともありますが、レンダリングの種類によっては設定に工夫が必要と知り、今回のポートフォリオ作成ではトラブル回避と開発スピードを最優先してVercelを採用しました。
  * **ドメイン運用:** DNS（ConoHa WING）側でCNAMEレコードを設定し、独自ドメイン（`material-request.asabori.com`）を紐付けて公開しています。

## 2. データベース / ORM / 認証
* **Neon (PostgreSQL)**
  * **選定理由:** 過去にレンタルサーバー（ConoHa WING）でMySQLを使用した際、ローカルと本番で接続設定を管理するのが難しく、動作確認のために本番環境へ切り替えた際に誤って本番データを直接操作してしまう危険性を感じました。DBの構築や運用は自力でやらずクラウドに頼る方が安全だと考えています。Supabaseも検討しましたが、GUIでの操作が多くAIに操作方法を聞いても画面の仕様変更などで正しい回答が得られにくく詰まりやすいため、よりシンプルにDB機能へ特化したNeonを選びました。また、GitHub ActionsでPlaywrightを実行する際、毎回Dockerで重いDBコンテナを立てるより、Neonのブランチ機能を使う方が軽量で扱いやすいと知ったため採用しました。
* **Drizzle ORM**
  * **選定理由:** PrismaとDrizzleの比較記事でコードを見比べた際、記号の使い方やコードの並びも含めて、Drizzleの方が自分にとって見慣れた形をしており、スムーズにコードを読めると感じたため採用しました。
* **Clerk**
  * **選定理由:** Supabaseのような多機能サービスで管理画面から複雑な設定をする手間や、自前実装の手間を省くためです。今回のポートフォリオは「QAエンジニアとしてPlaywrightを使ったテスト自動化」に力を入れることが最優先目的のため、認証は単体で分かりやすい専用サービス（Clerk）に頼り、本題のテスト開発に時間を割く判断をしました。

## 3. テスト / 自動化環境
* **Playwright**
  * **選定理由:** Cypressなどの他ツールと比較して、現在のWeb開発で主流になっていると聞いたためです。テスト同士が干渉して失敗しにくい仕組みになっている点や、画面上のマウス操作からテストコードを自動生成してくれる機能（`codegen`）があり、効率よくテスト作成を進められると感じたため採用しました。
* **GitHub Actions**
  * **採用目的:** リポジトリへのプルリクエスト作成などをトリガーにして、PlaywrightのE2Eテストを自動実行し、さらにVercelへのデプロイ連携までを自動化するCI/CD環境として活用しています。

## 4. 過去の技術体験と Next.js 採用までの経緯

今の構成（Next.js + Vercel）に至るまでに、いくつかの技術やツールを触って試行錯誤した経緯があります。今回のポートフォリオ自体はシンプルなWebアプリですが、過去の体験が今回の技術選定に繋がっています。

* **PHP/Laravel を触った体験とApp Routerへの感動**
  * 以前Laravelを触っていた際、当時は画面表示と処理を分けるMVCモデルの概念が難しく感じていました。
  * その後Next.jsのApp Routerを知った時、フォルダを作ってファイルを置くだけで自動的にURLが決まる仕組みを見て、「なんて画期的なんだ」と感動しました。この扱いやすさが、今回Next.jsを使いたいと思った一番のきっかけです。

* **Flutter（スマホアプリ開発）から Webアプリへ方向転換した理由**
  * 最初は「1つのコードでiPhoneもAndroidも動かせるなら最高だ」と思い、Flutterでスマホアプリを作ってみました。
  * しかし、設定画面を開く処理でOPPOのスマホ特有の制御に引っかかり、どうしても思うような動きにできずハマってしまいました。「クロスプラットフォームと言っても、結局は端末ごとの個別の仕組みを調べたり、ネイティブのコードを書かないといけない場面があるんだな」と気づきました。
  * また、「Flutterは独自の描画エンジンだからどこでも同じように表示できる」と聞いていましたが、スマホの画面サイズが違えば結局レイアウト調整（レスポンシブ対応）は当然必要で、決して楽できるわけではないと分かりました。
  * こうした泥臭い端末ごとの対応に悩む中で、PWAやTWAという仕組みや、GitHubにコードをPushするだけで自動デプロイできるサービス（Vercelなど）の存在を知りました。「端末ごとの個別対応はなるべく避けて、Webアプリとして作って公開する方がずっと合理的だ」と考え、Webアプリ開発に切り替えました。

* **「1つのリポジトリで複数のアプリを作る」案をやめた理由**
  * Next.jsを触り始めた当初、「Cloudflareの設定やドメイン（CNAME）の設定を1度で済ませたい」と考え、1つのリポジトリの中に App Router でディレクトリをどんどん増やして、複数のアプリを連投していく仕組みを思いつきました。
  * ですが、いざNext.jsの素のプロジェクトを作ってCloudflareに繋いだ段階で、ふと「個別のアプリから見たら、関係ないツールや設定ファイルが同じリポジトリの中にゴチャゴチャ混ざることになるな」と気づきました。
  * 余計な階層が増えてあとから構造がわかりにくくなりそうだと思い直し、アプリを作り始める前にこの案は取りやめ、シンプルに「1つのアプリにつき1つのリポジトリ」で作ることにしました。
