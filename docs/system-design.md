# 📐 システム・DB設計 (System Design)

システム全体のアーキテクチャ、データベース設計、およびクラス/モジュール分割の判断理由について記述します。

---

## 1. DB設計（ER図・トレードオフの意思決定）

### Q: `users` テーブルのカラム名を `clerk_user_id` とし、`auth_provider_id` 等に抽象化しなかった理由は？

**A: 抽象化によるオーバーエンジニアリングを避け、将来的な認証プロバイダ移行時の安全性を担保するためです。**

具体的な理由は以下の2点です。

1. **抽象化の費用対効果（ROI）が低い:**
   認証サービス（IdP）の変更は頻繁に起こるものではなく、発生確率が低いリスクに対して初めから抽象的なデータ構造を組むメリットが少ないと判断しました。
2. **移行時の安全性が高い（マルチカラム保持）:**
   もし将来 Clerk から別の IdP（例: Supabase Auth や Auth0）に移行する場合、`clerk_user_id` とは別に `supabase_user_id` などの新しいカラムを一時的に併設する方が、旧IDとのマッピングやデータ移行（マイグレーション）作業を段階的かつ安全に行えます。

### Q: プロフィール登録では、なぜ職員マスタと紐付けず、申請者自身に氏名や診療科を直接入力させるのか？

**A: データの厳格さや検索性よりも、現場の医師が入力しやすいUXを最優先したためです。**

1. **現場の医師の事情**
   * 医師の多くは「医局人事」により、大学病院系列内を定期的に、実質的な人事異動として転職してきます。
   * そのため、一般的な職員と異なり、院内で付番されている自身の「職員番号」を正確に把握しておらず、番号の入力を求めるのは不親切です。
   * また、院内電話番号についても、院内電話帳で全員分が網羅・検索できる運用になっており、申請フォームでわざわざ入力させる必要性がありません。

2. **本システムの目的への最適化**
   * 本システムは「診療材料審査委員会での申請・審査」が目的であり、委員会側で「どの診療科の誰が申請したか」が識別できれば十分機能します。
   * 本来、システム設計の定石としては職員マスタを参照して「表記揺れやタイポの防止」「検索性の向上」を図るべきですが、本要件においては「職員番号を調べる手間」を医師に強いるデメリットの方が大きいと判断しました。
